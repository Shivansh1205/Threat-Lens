Guarded by a new full-stack test, `test_unusual_ip_alert_fires_through_full_ingestion_endpoint`, which POSTs through the real endpoint rather than calling the detector directly.

- Phase 5 dynamic risk scoring: every alert's `score`/`severity` are now context-aware — combining the detector's raw call with the user's current behavioral `deviation_score` — instead of the fixed constant each detector previously hardcoded, plus a rolling per-user risk ranking.
  - `scoring/risk_scorer.py` — `RiskScorer.score_alert(candidate, profile)`: `adjusted = base_score + deviation_score * DEVIATION_WEIGHT * (100 - base_score)`, clamped to [0, 100] and rounded. The `(100 - base_score)` headroom term means behavioral novelty can meaningfully escalate a borderline MEDIUM/HIGH alert without ever catapulting a LOW alert straight to CRITICAL on novelty alone. At `deviation_score == 0.0` this is an exact identity (`adjusted == base_score`) by construction. Also `severity_for_score(score)` — the single shared bucketing function (LOW 0-25 / MEDIUM 26-50 / HIGH 51-75 / CRITICAL 76-100, now centralized as `SEVERITY_{LOW,MEDIUM,HIGH}_MAX` in config rather than living only in ARCHITECTURE.md prose) — and `RiskScorer.update_user_risk(profile, adjusted_score)`: `new = min(100, profile.user_risk_score * USER_RISK_DECAY_FACTOR + adjusted_score * RISK_CONTRIBUTION_WEIGHT)`, mutating `BehaviorProfile.user_risk_score` in place.
  - `models/alert.py` — added `raw_score`/`raw_severity` (NOT NULL): the detector's original, pre-adjustment call, preserved for auditability now that `score`/`severity` hold the risk-adjusted final values. `schemas/alert.py`'s `AlertOut` updated to expose both.
  - `models/behavior_profile.py` — added `user_risk_score` (Float, default 0.0, indexed): a rolling, decaying cumulative risk score per user, distinct from the per-event `deviation_score`. Users who never trigger an alert stay at 0.0 forever — correct, since they haven't earned a place on the high-risk ranking.
  - Migration `alembic/versions/20260801_0300_add_risk_scoring.py` (hand-written, not applied): adds both `alerts` columns as NOT NULL directly (no default/backfill — a real production deployment would need one; this is a dev database) and `behavior_profiles.user_risk_score` NOT NULL + indexed. Reuses the existing Postgres `severity` enum type for `raw_severity` (`create_type=False`) rather than re-declaring it.
  - Config additions: `DEVIATION_WEIGHT=0.3`, `RISK_CONTRIBUTION_WEIGHT=0.15`, `USER_RISK_DECAY_FACTOR=0.995`, `SEVERITY_{LOW,MEDIUM,HIGH}_MAX`.
  - `detection/registry.py` — `DetectorRegistry.run_all()` now takes a `profile: BehaviorProfile` parameter, scores every `AlertCandidate` via `RiskScorer.score_alert()`, calls `RiskScorer.update_user_risk()` once per alert (not once per event — an event that produces two alerts contributes twice), and persists the risk-adjusted `Alert` rows plus the mutated profile in one flush.
  - `GET /api/v1/users/high-risk?limit=` (new `api/users.py`, `schemas/user_risk.py`): users ranked by `user_risk_score` descending, excluding `user_risk_score == 0`, default limit 10 / max 100. Returns `{user_id, user_risk_score, login_count, known_ip_count, last_event_at}`.
  - **Documented v1 simplification:** `user_risk_score`'s decay is applied once per new alert EVENT for a user, not once per elapsed unit of TIME — a user who stops triggering alerts keeps their score forever rather than it fading with time. True time-based decay needs a scheduled/background job that doesn't exist yet; flagged as a named Phase 5.5/6+ follow-up in `PHASES.md` (Phase 4 section) rather than faked with an elapsed-time hack.
  - Test suite grows to 75 (was 59): new `tests/test_scoring/` — `test_risk_scorer.py` (9: no-op at zero deviation, low-/high-headroom escalation with exact expected values, explicit >100 clamp with an overridden weight, severity re-bucketing, bucket-boundary exactness, rolling-risk first-update/accumulation/damping-under-repeated-small-scores), `test_high_risk_users_endpoint.py` (5: empty DB, zero-score exclusion, descending order, `limit`, known-IP count), `test_registry_with_scoring.py` (2: a high-deviation user's persisted alert differs from the Phase 3 raw expectation while `raw_score`/`raw_severity` still match it exactly; a zero-deviation user's adjusted values equal raw exactly). `tests/test_detection/test_registry.py` updated for `run_all()`'s new `profile` parameter (a helper builds a deviation_score=0.0 profile per test, confirming these Phase 3 tests still hold unchanged at zero deviation).
- Phase 6 AI-assisted explainability: every alert gets an LLM-generated explanation + a constrained mitigation checklist (local Ollama/Mistral), generated out-of-band so ingestion latency never depends on the LLM, plus a retrieval-augmented chatbot grounded on recent alerts.
  - `ai/ollama_client.py` — `generate(prompt, timeout) -> str | None`, the sole HTTP boundary to Ollama's `/api/generate`. Never raises: connection errors, timeouts, non-200s, and malformed JSON envelopes all collapse to a logged `WARNING` + `None` return, which is what makes every caller's graceful-degradation path unit-testable without a real Ollama instance.
  - `ai/explainability.py` — `ExplainabilityEngine`: `build_prompt(alert, event, profile)` includes the alert's raw AND adjusted score/severity (with an explicit note when they differ, since that delta — behavioral novelty drove an escalation — is itself useful analyst context), the triggering event's type/IP/timestamp, behavioral context (known-IP count, deviation_score, user_risk_score, login_count), and a fixed mitigation vocabulary (`MITIGATION_VOCABULARY`: block IP, force password reset, require MFA re-enrollment, notify user via secondary channel, temporarily lock account, review recent account activity, no action needed/monitor) the model must select 2-5 items from rather than inventing its own wording. `explain(alert_id)` fetches the Alert/LogEvent/BehaviorProfile fresh from the DB (never assumes objects from the request that created the alert are still attached), calls Ollama, and on success updates `alert.explanation`/`alert.mitigation_steps` and commits; on any failure (Ollama down, timeout, unparseable response) leaves both NULL — no partial/garbage writes.
  - **Parsing strategy: delimited text (`EXPLANATION:`/`MITIGATION:` markers), not JSON.** Local 7B-class models running zero-shot through Ollama are not reliably strict-JSON-safe — stray preamble, trailing code fences, smart quotes, or a truncated brace all break `json.loads` outright with zero partial credit. Marker-based parsing degrades gracefully instead: markers can still be found even inside extra prose, and mitigation lines are only ever accepted if they contain one of the fixed vocabulary phrases (case-insensitive substring match) — everything else is dropped rather than trusted. This gets most of JSON's structure-safety without JSON's all-or-nothing fragility.
  - `ai/chatbot.py` — `ChatbotModule`: `build_context(db, user_id, limit=20)` formats recent alerts (optionally filtered by user_id) into compact text for prompt injection (the retrieval half of retrieval-augmented chat — the model only ever sees what this returns). `handle_query(session_id, message, db)` does a basic substring mention-check against known `user_id`s (not real NLU — a bounded v1 heuristic, longest match wins), builds context, injects capped conversation history, calls Ollama, and returns an honest fallback ("I'm unable to reach the AI assistant right now...") rather than a fabricated answer when Ollama is unreachable. Conversation history is an in-memory, module-level dict keyed by `session_id`, capped at the last 10 exchanges (oldest dropped first) — same ephemeral tier as detector sliding windows; a real multi-process deployment would need this in Redis or a DB table (Phase 7+ concern).
  - `POST /api/v1/chat` (new `api/chat.py`): `{session_id, message}` -> `{response}`. Wired into `main.py`.
  - **Non-blocking ingestion (the central design constraint of this phase):** `POST /api/v1/log` persists new alerts with `explanation`/`mitigation_steps` still NULL and schedules `generate_explanation_task` via FastAPI's `BackgroundTasks` (Starlette-native, no new dependency) instead of calling Ollama inline — an LLM call can take several seconds, and doing that synchronously inside ingestion would make request latency depend on Ollama, exactly the kind of coupling that caused connection-pool exhaustion under bursty load in earlier phases (Phase 3/4), just worse. `generate_explanation_task(alert_id, db_session_factory)` opens its own DB session (the request's session may already be closed by the time a background task runs) and never propagates an exception. `GET /api/v1/alerts` legitimately returning `explanation: null` for a very recent alert is expected behavior, not a bug. TODO noted in code: no retry-with-backoff yet — a real task queue (Celery/arq) would be the natural place to add it.
  - Config additions: `LLM_TIMEOUT_SECONDS=15.0` (existing `OLLAMA_HOST`/`OLLAMA_MODEL` from the Phase 2 scaffold were unused until now).
  - **Investigated and documented, not assumed:** FastAPI/Starlette's `TestClient` runs `BackgroundTasks` synchronously, inline, before `client.post(...)` returns — confirmed directly with a throwaway script (a background task that `asyncio.sleep(1.0)` made `TestClient.post()` itself take ~1.01s). This is because `TestClient` drives the ASGI app in-process with no real socket separating "response sent" from "background task runs" (unlike a real uvicorn deployment, where the response is flushed to the client's socket first and the background task then runs after, within the same worker). Documented in `tests/test_ai/test_ingestion_with_background_tasks.py`'s module docstring; the non-blocking *design* is proven independent of this TestClient quirk by asserting `ingest_log` schedules `generate_explanation_task` via `add_task` (deferred) rather than awaiting it inline.
  - Test suite grows to 101 (was 75): new `tests/test_ai/` — `test_ollama_client.py` (6: success, connection error, timeout, malformed JSON, non-200, missing response field — all mocking `httpx.AsyncClient` directly, zero real network calls), `test_explainability.py` (7: valid response updates the alert, Ollama-down and unparseable-response both leave fields NULL without raising, a response with zero recognizable vocabulary items is rejected wholesale, a missing alert_id doesn't raise, `build_prompt` content assertions for both the escalated and unchanged-score cases), `test_chatbot.py` (7: context with/without user_id filtering, empty-DB context, mocked-response history update, honest fallback on Ollama-down, user_id mention detection via a captured prompt, history capped at `MAX_HISTORY_EXCHANGES`), `test_ingestion_with_background_tasks.py` (2: fast response with alerts created, structural proof of deferred scheduling), `test_chat_endpoint.py` (4: mocked success, Ollama-down fallback, two 422s for missing required fields). A new `anyio_backend` fixture (in `conftest.py`, restricted to `"asyncio"`) lets `async def` tests run via anyio's pytest plugin — already a transitive dependency of fastapi/httpx/starlette — without adding `pytest-asyncio`.
- Phase 7a real-time delivery: new alerts now push to connected dashboard clients over WebSocket instead of relying solely on the frontend's 5s poll (that poll isn't removed yet — this prompt is backend-only; Prompt 7b wires the frontend client).
  - `realtime/websocket_manager.py` — `WebSocketManager`: `connect(websocket) -> client_id` (accepts + registers), `disconnect(client_id)`, `async broadcast(message)` (sends to every connected client; a send failure on any one client is caught, logged, and that client is dropped — it never aborts the loop for the rest), `async send_personal(client_id, message)` (implemented ahead of need, for a possible future chatbot-over-websocket use). Module-level singleton `get_ws_manager()` / `reset_ws_manager()` (test isolation), same lazy-singleton pattern as `detection.registry.get_registry()`. TODO(Phase 8+) noted for Redis pub/sub if this ever moves to multiple uvicorn worker processes — an in-memory per-process dict is correct only for this project's single-worker deployment.
  - `POST /ws/alerts` → actually `@router.websocket("/ws/alerts")` (new `api/websocket.py`), mounted in `main.py` WITHOUT the `/api/v1` prefix (reachable at `ws://host:port/ws/alerts`, matching ARCHITECTURE.md's real-time delivery diagram) — REST endpoints are versioned because their request/response shapes evolve independently; this socket carries one push message shape and versioning it alongside REST would be premature. Accepts the connection via the manager, then loops on `receive_text()` (required so the protocol doesn't consider the connection dead, and so `WebSocketDisconnect` is raised on client-close), disconnecting via the manager in a `finally` block.
  - **Sync/async broadcast resolution (the central design question of this phase):** `POST /api/v1/log` stays a *sync* `def` endpoint rather than becoming `async def`. Converting it would move it off Starlette's threadpool (real OS threads — the whole reason Phase 4 needed `threading.Lock` in the two stateful detectors) onto the single main event loop; since every DB call in the ingestion pipeline is synchronous SQLAlchemy (never `await`-ed), an async endpoint would in practice serialize every request on that one loop thread instead of running them genuinely concurrently — a throughput regression under bursty ingestion, not an improvement. Instead, broadcasting is dispatched via a new sync method, `WebSocketManager.schedule_broadcast(message)`, which hands the actual `async def broadcast()` call to the main event loop via `asyncio.run_coroutine_threadsafe` — the correct bridge for "run async code, from a different thread, on a specific already-running loop." (`asyncio.run()` was explicitly rejected: it would spin up a new throwaway loop per call inside the worker thread and try to drive WebSocket objects bound to the MAIN loop from that foreign loop, which asyncio doesn't support safely.) The main loop is captured once via a new `lifespan` handler in `main.py` (replacing the previously-absent startup/shutdown hooks) — `get_ws_manager().set_loop(asyncio.get_running_loop())` — since async endpoints and the lifespan handler itself run directly on that loop.
  - `api/logs.py`: after the existing single commit, for each newly persisted alert, `get_ws_manager().schedule_broadcast({...})` with a deliberately small payload — `id`, `user_id`, `alert_type`, `severity`, `score`, `message`, `created_at`. `explanation`/`mitigation_steps` are NOT included (they don't exist yet at push time — generated moments later by the Phase 6 background task; the frontend can re-fetch full details on demand). Whether a second "alert updated" push should fire once the explanation lands is left as an open choice for Prompt 7b, not resolved here. Broadcast happens strictly after `db.commit()`, never before, so nothing that could still roll back gets pushed.
  - `tests/conftest.py`'s shared `client` fixture now enters `TestClient` as a context manager (`with TestClient(app) as c:`) rather than just constructing it — required both for `lifespan` to actually run in tests (needed for `set_loop`) and for `TestClient.websocket_connect(...)` to work at all. A new `_fresh_ws_manager` autouse fixture resets the manager singleton between tests, same rationale as `_fresh_detector_state`.
  - **Investigated and confirmed empirically, not assumed:** the full round-trip (`POST /api/v1/log` on the threadpool → `schedule_broadcast` → `run_coroutine_threadsafe` onto TestClient's portal loop → live `/ws/alerts` connection receiving the message) works correctly under `TestClient`'s execution model — proven directly by `test_alert_broadcast_reaches_connected_client`, not just asserted in theory, and confirmed stable across 5 repeated runs.

- Time-based `user_risk_score` decay — closes the Phase 4/5 documented gap where a user's rolling risk score only ever decayed when they triggered a *new* alert, meaning a user flagged once and then quiet for months kept whatever score they last had, indefinitely. This is additive: the existing per-alert-event decay (`RiskScorer.update_user_risk`, `USER_RISK_DECAY_FACTOR`) is completely unchanged.
  - `app/scoring/decay_job.py` (new) — `run_decay_pass(db, settings) -> dict`: for every `BehaviorProfile` with `user_risk_score > DECAY_SCORE_FLOOR`, computes `decayed = score * (DAILY_DECAY_RATE ** days_elapsed)` using real elapsed time (`days_elapsed = (now - profile.updated_at).total_seconds() / 86400.0`, falling back to `created_at` if `updated_at` is still NULL) rather than a flat per-run multiply — the job might not run exactly every 24h (downtime, missed runs), so decay reflects actual elapsed time, not run count. Results below the floor clamp to exactly `0.0` rather than left as an ever-shrinking non-zero remainder. Pure DB-session-in/dict-out (`profiles_processed`, `profiles_decayed`, `total_score_removed`), flushes but does not commit (same pattern as `BehaviorProfiler`'s methods) — independently testable with no scheduler or FastAPI app running.
  - **Worked through with real numbers (not just asserted) why resetting `updated_at` after every decay pass is safe, not a bug:** exponential decay composes exactly under repeated multiplication of the same rate over sub-intervals (`rate**(t1+t2) == rate**t1 * rate**t2`). For a starting score of 50.0 at the default rate 0.98: one pass after 10 elapsed days gives `50.0 * 0.98**10 ≈ 40.86`; ten passes one elapsed day apart each — which is what the "run on startup + every 24h" schedule actually produces in practice, since each pass resets `updated_at` and the next pass measures the 1.0 days since — gives `50.0 * (0.98**1)**10 == 50.0 * 0.98**10`, the identical value. So frequent/repeated decay passes converge to the same result as one pass after the equivalent total elapsed time; they do not over-decay. This also explains why a profile touched by a fresh per-event decay a few hours ago sees negligible decay from this job on the same day (`0.98**(3/24) ≈ 0.9975`) — correct, since the per-event mechanism already accounted for that day's activity.
  - Config additions: `DAILY_DECAY_RATE=0.98` (halves an untouched score in ~34 days: `0.98**34 ≈ 0.5`), `DECAY_JOB_INTERVAL_HOURS=24.0`, `DECAY_SCORE_FLOOR=0.01`.
  - **Scheduler: APScheduler (`AsyncIOScheduler`), not a real task queue.** Considered and rejected Celery/arq as infrastructure overkill for this project's single-process deployment; APScheduler is a lightweight, in-process library that hooks directly into the same FastAPI `lifespan` handler Phase 7a already uses to capture the event loop for WebSocket broadcasting. `main.py`'s `lifespan` now also starts an `AsyncIOScheduler` with an interval trigger (every `DECAY_JOB_INTERVAL_HOURS`) plus one immediate run on startup (so decay is observable without waiting a full interval during development/demo), and calls `scheduler.shutdown(wait=False)` on app shutdown. Interval trigger chosen over a fixed wall-clock time (e.g. "run at 03:00") for simplicity and to avoid timezone questions at this project's scale — noted in code as something a production deployment would likely want to reconsider.

Verified this required change causes zero regressions by running the full existing suite against it.

### Fixed
- Phase 3 mid-loop `DetachedInstanceError` under real HTTP: `DetectorRegistry.run_all` now flushes (endpoint owns commit) so ORM `LogEvent` instances still held in a detector's sliding window aren't expired between events, and `PortScanDetector` snapshots the per-event values it needs (`ts`, `port`, `ip`, `event_id`) at observation time so it never re-reads an expired ORM attribute. Verified end-to-end against a live uvicorn: `brute_force` → 4/4 alerts (MEDIUM, HIGH, CRITICAL brute_force + CRITICAL brute_force_success), `port_scan` → 2/2 (HIGH at 15 distinct ports, CRITICAL at 50), `unusual_ip` → 1/1 LOW.
- **Concurrency race in `BruteForceDetector` and `PortScanDetector`**, found by Phase 4 live verification: `--speed 100` produced 5 alerts instead of 4 (duplicate MEDIUM and duplicate HIGH, 7-16ms apart) with the CRITICAL alert missing entirely. Root cause: `POST /api/v1/log` is a sync endpoint, so Starlette runs it on threadpool worker threads, and `DetectorRegistry` holds one process-wide singleton instance of each detector — concurrent requests for the same user_id/ip were reading and writing the shared `self._windows` / `self._last_emitted` dicts with no synchronization. Two threads could both read `last_emitted=0` before either wrote it (duplicate alerts), and unguarded concurrent mutation of the same window could corrupt state outright — reproduced directly as `RuntimeError: deque mutated during iteration` in `PortScanDetector` when forced to race. Fixed with a single `threading.Lock` per detector instance guarding the full read-decide-write section in `check()` (global, not per-key — the critical section is a handful of dict/deque operations with no I/O, so serializing it process-wide costs nothing measurable at this project's scale; a per-key locking scheme would only add bookkeeping complexity for no real win here). `UnusualIpDetector` needed no change — Phase 4 already made it fully stateless. New `tests/test_detection/test_concurrency.py` (3 tests) proves this with real OS threads: confirmed to fail without the lock (duplicate `['MEDIUM', 'MEDIUM']` for brute-force via a deterministic forced-interleave technique — natural GIL scheduling essentially never lands inside that particular narrow critical section, 0/90+ attempts, even though the race is real; `deque mutated during iteration` for port-scan via natural concurrent execution, ~70% of runs) and to pass reliably with it (5/5 clean runs each). Re-verified end-to-end at `--speed 100` (no `--speed 10` workaround needed): 5/5 clean runs for both `brute_force` (exactly `[CRITICAL, CRITICAL, HIGH, MEDIUM]`) and `port_scan` (exactly `[CRITICAL, HIGH]`), zero errors.
- `POST /log` user upsert now uses `postgresql.insert(...).on_conflict_do_update(...)` for concurrency-safe inserts (compiles to SQL that both Postgres and SQLite 3.24+ accept, so the test suite still runs in-memory).

## How to log a change

When you land a PR that touches user-visible behavior, add a line to `## [Unreleased]` under the right heading:

- **Added** — new features or capabilities.
- **Changed** — modifications to existing behavior (breaking or not).
- **Fixed** — bug fixes.
- **Removed** — things taken out.
- **Deprecated** — things marked for future removal.
- **Security** — vulnerability fixes.

Keep entries concise: what changed, not why. Save the "why" for the commit message and the PR description.

When you cut a release, rename `[Unreleased]` to the version and date, then create a new empty `[Unreleased]` on top.
