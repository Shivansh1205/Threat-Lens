- Root `.gitignore` for Python, Node, env files, and editor/OS artifacts.
- Phase 2 end-to-end skeleton pipeline: a log event can be POSTed, validated, persisted, run through a stub detector, and surfaced as an alert in the frontend.
  - Database models (`backend/app/models/`): `User`, `LogEvent` (with verbatim `raw_json` audit column), `Alert` — using cross-backend column types (generic `Uuid`; `JSONB` on Postgres with a `JSON` variant for SQLite tests).
  - Pydantic schemas (`backend/app/schemas/`): strict `LogEventIn` (rejects unknown fields), `LogEventOut`, `AlertOut`, and shared `EventType`/`Severity` enums in `common.py` (single source of truth for models and schemas).
  - Initial Alembic migration `alembic/versions/20260731_1513_initial_schema.py` for the three tables and their indexes (autogenerated; not applied).
  - `POST /api/v1/log` — validates payload, upserts the `User` (`last_seen_at` on repeat), persists the `LogEvent`, runs detection synchronously, returns `201` with the event id and any alert ids.
  - Stub detector (`backend/app/detection/stub.py`): any `LOGIN_FAILURE` raises a LOW alert (score 15, `failed_login`). Placeholder — Phase 3 replaces it with the real engine.
  - `GET /api/v1/alerts?limit=&user_id=&severity=` — most-recent-first, with optional filters.
  - Backend tests (`test_log_ingestion.py`, `test_alerts.py`) on a per-test in-memory SQLite DB via a `get_db` override; full suite passes (8 tests).
  - Frontend proof-of-flow: `hooks/useAlerts.js` (fetches `/api/v1/alerts` on mount, polls every 5s), `components/AlertList/AlertList.jsx` (table with color-coded severity badge), `pages/Dashboard.jsx`, wired as the default route in `App.jsx` with minimal Tailwind.
- Phase 3 real detection engine — rule-based, in-memory, single-process (Redis-backed state is a Phase 6+ concern; behavioral profiling is Phase 4).
  - `detection/sliding_window.py`: generic deque-backed `SlidingWindow` with eviction driven by event timestamps (not wall clock) so detectors are deterministic and testable. Timestamps are snapshotted to naive UTC at `add()` time to survive ORM refresh quirks under SQLite.
  - `detection/base.py`: `Detector` ABC and `AlertCandidate` dataclass. Detectors are pure — they observe events and yield candidates, they never write to the DB.
  - `detection/rules/brute_force.py` — `BruteForceDetector`: per-user 60s failure window, escalates once per crossed threshold (MEDIUM at 5, HIGH at 10, CRITICAL at 20); a subsequent `LOGIN_SUCCESS` within the window emits a separate CRITICAL `brute_force_success` alert and clears state.
  - `detection/rules/port_scan.py` — `PortScanDetector`: per-IP 3s window, alerts on distinct-port count (HIGH at 15, CRITICAL at 50). Same port hit repeatedly does not count.
  - `detection/rules/unusual_ip.py` — `UnusualIpDetector`: per-user known-IP set with a 3-login bootstrap (silent), then LOW alert on any new IP; TODO to fold into `BehaviorProfiler` in Phase 4.
  - `detection/registry.py`: `DetectorRegistry` runs all detectors per event and is the only place that persists `Alert` rows (`db.add_all` + `commit` + `refresh`). Lazy module-level singleton via `get_registry()`, with `reset_registry()` for test isolation.
  - Config additions: `BRUTE_FORCE_{WINDOW_SECONDS,MEDIUM,HIGH,CRITICAL}_THRESHOLD`, `PORT_SCAN_{WINDOW_SECONDS,HIGH,CRITICAL}_THRESHOLD`, `UNUSUAL_IP_BOOTSTRAP_COUNT` — all readable from env, all with the spec defaults.
  - `api/logs.py` now calls the real registry; the Phase 2 stub (`detection/stub.py`) is retired to reference-only and no longer registered.
  - Test suite grows to 39 tests (was 8): `tests/test_detection/` covers the sliding window, each detector (thresholds, escalation, state-keying, no-cross-contamination), and the registry (persistence + `triggered_by_event_id` linkage + a guard that the stub is not registered). Existing log-ingestion and alert tests updated for the new "single failure is silent" behaviour; a `_fresh_detector_state` autouse fixture resets the registry between tests.
  - `scripts/generate_logs.py` real implementation: `asyncio` + `httpx.AsyncClient`, `--scenario {normal,brute_force,port_scan,unusual_ip,mixed}`, `--target-url`, `--speed` multiplier; each scenario prints `Sent N events over Ds. Expected M alerts.`
- Phase 4 behavior profiling: a persistent, per-user baseline that survives restarts, plus deviation scoring (not yet used for alerts — that's Phase 5's RiskScorer).
  - `models/behavior_profile.py` — `BehaviorProfile`: `known_ips` (JSONB/JSON list), `login_count`, EMA pairs `typical_login_hour`/`login_hour_variance` and `typical_days_between_logins` (two floats each, not a 24-bin histogram — decays naturally, cheap to store), `last_login_at`/`last_logout_at`, `avg_session_duration_seconds` (EMA), `total_sessions`, rolling `deviation_score`, and `last_event_at` as the dedup key.
  - `schemas/behavior_profile.py` — `BehaviorProfileOut`, ahead of the Phase 5 endpoint that will return it.
  - Migration `alembic/versions/20260801_0101_add_behavior_profiles.py` (autogenerated against the existing 3-table schema so it only picks up `behavior_profiles` + its index; not applied).
  - `profiling/profiler.py` — `BehaviorProfiler`: `get_or_create` (upsert via `ON CONFLICT DO NOTHING` + fetch, race-safe for a burst of first-events), `update()` (dedups on `event.timestamp <= last_event_at`, EMA-updates login-hour/variance/days-between-logins on login events, session duration on LOGOUT paired with the last LOGIN), `compute_deviation()` (0.0–1.0, mean of nonzero `ip_novelty`/`hour_deviation`/`frequency_deviation` components), `get_known_ips()`, `is_past_bootstrap()`. One shared `EMA_ALPHA` (config, default `0.05`) for every EMA — no per-metric tuning.
  - `UnusualIpDetector` rewritten fully stateless: no more in-memory `{user_id: set[ip]}` / login-count dicts. Reads `known_ips` and bootstrap status straight from the DB via `BehaviorProfiler` on every call — known IPs now survive a server restart (see `test_unusual_ip_persists_across_restart`).
  - **Pipeline-ordering fix (found during implementation, not spec'd):** `BehaviorProfiler.update()` unconditionally folds the current event's IP into `known_ips`. Updating the profile *before* running detection (as originally sequenced) would make `UnusualIpDetector` always find its own event's IP already "known" and never fire — a working detector in isolated unit tests, silently dead in production. `POST /api/v1/log` now runs the detector registry *before* `profiler.update()`; `is_past_bootstrap()` uses `>=` rather than `>` to compensate (login_count is now read pre-increment for the current event) and lands on the same boundary (4th login = first non-bootstrap, with the default `UNUSUAL_IP_BOOTSTRAP_COUNT=3`). Guarded by a new full-stack test, `test_unusual_ip_alert_fires_through_full_ingestion_endpoint`, which POSTs through the real endpoint rather than calling the detector directly.
  - Test suite grows to 56 tests (was 40): `tests/test_profiling/` (profiler EMA/dedup/session-duration/deviation-score behavior, 11 tests; profiler-backed detector behavior including the restart-persistence test, 3 tests), plus 2 new `tests/test_log_ingestion.py` tests (profile built via the real endpoint; the ordering regression guard above). `tests/test_detection/test_unusual_ip.py` rewritten against the profiler (same assertions, new setup); `test_registry.py` needed no changes.

### Changed
- Increased the SQLAlchemy connection pool (`DB_POOL_SIZE=20`, `DB_MAX_OVERFLOW=40`, both configurable via `.env`) to stop `QueuePool` timeouts / 500s under bursty log ingestion.
- `POST /api/v1/log` now runs detection *before* updating the behavior profile for the same event (not after, as originally sequenced) — see Fixed, below.

### Fixed
- Phase 3 mid-loop `DetachedInstanceError` under real HTTP: `DetectorRegistry.run_all` now flushes (endpoint owns commit) so ORM `LogEvent` instances still held in a detector's sliding window aren't expired between events, and `PortScanDetector` snapshots the per-event values it needs (`ts`, `port`, `ip`, `event_id`) at observation time so it never re-reads an expired ORM attribute. Verified end-to-end against a live uvicorn: `brute_force` → 4/4 alerts (MEDIUM, HIGH, CRITICAL brute_force + CRITICAL brute_force_success), `port_scan` → 2/2 (HIGH at 15 distinct ports, CRITICAL at 50), `unusual_ip` → 1/1 LOW.
- **Concurrency race in `BruteForceDetector` and `PortScanDetector`**, found by Phase 4 live verification: `--speed 100` produced 5 alerts instead of 4 (duplicate MEDIUM and duplicate HIGH, 7-16ms apart) with the CRITICAL alert missing entirely. Root cause: `POST /api/v1/log` is a sync endpoint, so Starlette runs it on threadpool worker threads, and `DetectorRegistry` holds one process-wide singleton instance of each detector — concurrent requests for the same user_id/ip were reading and writing the shared `self._windows` / `self._last_emitted` dicts with no synchronization. Two threads could both read `last_emitted=0` before either wrote it (duplicate alerts), and unguarded concurrent mutation of the same window could corrupt state outright — reproduced directly as `RuntimeError: deque mutated during iteration` in `PortScanDetector` when forced to race. Fixed with a single `threading.Lock` per detector instance guarding the full read-decide-write section in `check()` (global, not per-key — the critical section is a handful of dict/deque operations with no I/O, so serializing it process-wide costs nothing measurable at this project's scale; a per-key locking scheme would only add bookkeeping complexity for no real win here). `UnusualIpDetector` needed no change — Phase 4 already made it fully stateless. New `tests/test_detection/test_concurrency.py` (3 tests) proves this with real OS threads: confirmed to fail without the lock (duplicate `['MEDIUM', 'MEDIUM']` for brute-force via a deterministic forced-interleave technique — natural GIL scheduling essentially never lands inside that particular narrow critical section, 0/90+ attempts, even though the race is real; `deque mutated during iteration` for port-scan via natural concurrent execution, ~70% of runs) and to pass reliably with it (5/5 clean runs each). Re-verified end-to-end at `--speed 100` (no `--speed 10` workaround needed): 5/5 clean runs for both `brute_force` (exactly `[CRITICAL, CRITICAL, HIGH, MEDIUM]`) and `port_scan` (exactly `[CRITICAL, HIGH]`), zero errors.
- `POST /log` user upsert now uses `postgresql.insert(...).on_conflict_do_update(...)` for concurrency-safe inserts (compiles to SQL that both Postgres and SQLite 3.24+ accept, so the test suite still runs in-memory).

## How to log a change

When you land a PR that touches user-visible behavior, add a line to `## [Unreleased]` under the right heading:

- **Added** — new features or capabilities.
- **Changed** — modifications to existing behavior (breaking or not).
- **Fixed** — bug fixes.
- **Removed** — things taken out.
- **Deprecated** — things marked for future removal.
- **Security** — vulnerability fixes.

Keep entries concise: what changed, not why. Save the "why" for the commit message and the PR description.

When you cut a release, rename `[Unreleased]` to the version and date, then create a new empty `[Unreleased]` on top.
